# CONTRIBUTING

Спасибо за интерес к проекту **Sungero Remote Component React Starter**.

Документ описывает базовые правила разработки, оформления изменений и подготовки Pull Request.

## Общие принципы

- Старайтесь вносить изменения небольшими и логически завершёнными частями
- Не смешивайте в одном PR рефакторинг, новую функциональность и массовое форматирование
- Поддерживайте совместимость с архитектурой remote-компонентов и standalone-песочницы
- По возможности покрывайте новую логику тестами

## Требования к окружению

Перед началом работы убедитесь, что установлены:

- Node.js 18+ или совместимая актуальная LTS версия
- npm

Установка зависимостей:

```bash
npm install
```

## Основные сценарии разработки

### Локальная разработка standalone-песочницы

```bash
npm run start:standalone:dev
```

Скрипт:

- подготавливает host-ассеты
- генерирует runtime-метаданные компонента
- запускает standalone dev-server

### Сборка standalone в режиме наблюдения

```bash
npm run build:standalone:dev
```

### Разработка remote-бандла

```bash
npm run watch:remote
```

### Локальный запуск remote-сборки

```bash
npm run start:remote:dev
```

### Production-сборка remote-компонента

```bash
npm run build:remote
```

## Генерация метаданных

Runtime-метаданные компонента генерируются на основе:

```text
config/component.manifest.js
```

Полезные команды:

```bash
npm run generate:component-metadata
npm run watch:component-metadata
```

Если вы добавляете новый контрол, loader или локализованное имя, убедитесь, что обновили manifest.

## Качество кода

Перед отправкой изменений рекомендуется выполнить:

```bash
npm run typecheck
npm run check
npm run test
```

Дополнительно доступны:

```bash
npm run lint
npm run format
npm run check:write
npm run test:coverage
```

### Что проверяется

- TypeScript-типизация
- линтинг и форматирование через Biome
- модульные тесты через Jest

## Тестирование

В проекте используется **Jest**.

Рекомендуется добавлять тесты для:

- утилит
- преобразования данных
- standalone stubs / fixtures
- container-логики контролов
- React-компонентов, если изменение затрагивает UI-поведение

Тесты можно размещать:

- рядом с исходным кодом: `*.test.ts`, `*.test.tsx`
- либо в отдельной директории тестов, если такой подход используется в модуле

Запуск тестов:

```bash
npm run test
```

Проверка покрытия:

```bash
npm run test:coverage
```

## Рекомендации по архитектуре

### 1. Разделяйте container и view

Предпочтительно разделять:

- **container-компонент** — работа с host API, подготовка данных, оркестрация
- **view-компонент** — отображение и UI-логика

### 2. Не завязывайте UI напрямую на host API

Если возможно, выносите интеграционную логику из presentational-компонентов.

### 3. Для standalone используйте stubs и fixtures

Для локальной разработки и тестирования предпочтительно использовать:

- stubs
- fixtures
- host model factories

а не встраивать тестовые данные прямо в UI-компоненты.

### 4. Не хардкодьте runtime-конфигурацию в компонентах

URL внешних сервисов, origin и другие runtime-параметры должны извлекаться через общий resolver/config-слой, а не задаваться прямо в контролах.

### 5. Учитывайте ограничения host-среды

Remote-компонент встраивается в host через Module Federation, поэтому при внесении изменений важно учитывать:

- совместимость shared-зависимостей
- особенности runtime host
- отсутствие прямой привязки к standalone-окружению

## Добавление нового remote-контрола

Обычно требуется:

1. Реализовать React-компонент в `src/controls/`
2. Добавить loader в `src/loaders/`
3. Зарегистрировать loader в `src/federation/component.loaders.ts`
4. Обновить `config/component.manifest.js`
5. При необходимости добавить standalone host model / stubs / fixtures
6. Добавить локализацию в `src/i18n/resources/`

## Стиль кода

- Используйте TypeScript
- Предпочитайте явные и понятные типы
- Не используйте non-null assertion (`!`) без крайней необходимости
- Не хардкодьте магические значения, если их можно вынести в конфиг, константу или helper
- Старайтесь сохранять существующий стиль именования файлов и сущностей внутри модуля

## Оформление коммитов

Жёсткого формата commit message не требуется, но рекомендуется:

- писать короткий и понятный заголовок
- при необходимости добавлять пояснение в теле коммита
- избегать сообщений вида `fix`, `changes`, `update` без контекста
- приветствуется использование `Conventional Commits`

Хорошие примеры:

- `feat: add standalone host model for performed work details grid`
- `fix: react-data-grid typings for local sandbox`
- `refactor: host stubs and add change notifier`

## Pull Request

Перед созданием PR убедитесь, что:

- код собирается
- `npm run typecheck` проходит без ошибок
- `npm run check` проходит без ошибок
- `npm run test` проходит успешно
- обновлены тесты, если менялась логика
- обновлена документация, если поменялся сценарий использования или структура проекта

### В описании PR желательно указать

- что изменено
- зачем это изменено
- как проверить изменение
- есть ли ограничения, риски или временные workaround'и

## Если вы меняете инфраструктуру проекта

Если PR затрагивает:

- webpack-конфигурацию
- Module Federation
- manifest/metadata generation
- standalone sandbox
- shared host API contracts

желательно отдельно описать это в PR и указать возможное влияние на интеграцию с host.

## Вопросы и обсуждение

Если изменение архитектурное, затрагивает взаимодействие с host или требует нестандартного решения, лучше заранее обсудить подход до реализации большого PR.
